# 运动修正报告

本报告对应一次针对"轨迹不正常、不连贯、不符合常识"的排查与修复。结论先行：

- 根因不是一个 bug，而是**同一类错误重复出现**——在函数不光滑的地方求导或反插，得到"一半的值"或"一个台阶"。本次共四处：seeker 反解（76.9 g）、航点切线缩放（0.035 m/s 速度台阶）、弧长反查（每个航点的速度台阶）、诊断工具步长（3e-3 的假导数误差）。前三处是产品代码的真实缺陷，第四处是检查工具本身在误报。
- 全库 32 个场景、102 个对象，违规从 **4061 条降到 0 条**，没有靠放宽阈值实现：降的是**判据的适用范围**（哪些对象该受气动约束）和**真实的运动缺陷**。
- 115 个测试全绿，其中 `tests/test_motion_realism.py` 的 25 个是本次新增的运动合理性测试。

---

## 1. 那个 76.9 g 到底怎么回事

### 现象

`sk_air_uav`（无人机视角，目标 8 km 外接近）第 0 帧速度只有后续帧的一半，加速度 754.4 m/s² = 76.9 g。

### 根因

不是速度算错，是**在两个地方对同一个不可导的量求导**：

1. `target_pos(t)` 把归一化进度做了钳位 `u = min(max(t/dur, 0), 1)`。
2. `target_vel(t)` 对 `target_pos` 做中心差分。

于是 t=0 处的差分样本 `u(-h)` 和 `u(+h)` **落在钳位面的同一侧**，分子只拿到了单边增量，除以 2h 就得到一半的斜率。

```
t=0.0   |v| =  75.846 m/s   <- 真实值的一半
t=0.1   |v| = 151.436 m/s
t=1.0   |v| = 150.840 m/s
```

### 修法

- 删掉钳位。位移本身是解析式，其导数是闭式的，不需要差分。
- 新增 `_seek_state(t)` 返回 `(position, velocity)` 的解析对，`target_vel` 直接取第二项。

### 修后

```
frame 0   t= 0.0  |v| = 150.9868   |v - dpos/dt| = 6.7e-09
frame 1   t= 0.1  |v| = 150.9809   |v - dpos/dt| = 2.4e-09
frame 49  t= 4.9  |v| = 150.7208   |v - dpos/dt| = 5.4e-09
```

首帧不再是半速，速度在全场景恒为 150.72–150.99 m/s，加速度 1.025 m/s²（0.10 g）。

### 为什么这条比单个 bug 重要

这是**方法论的错**，不是算式的错：只要"在不可导点做中心差分"这个模式还在，同一个 bug 会以不同外表反复出现。本报告第 2、3 节就是它在另外两个地方的复发。

## 2. 端点/边界的通用修法

### 为什么 t=0 特别危险

中心差分 `(f(t+h) - f(t-h)) / 2h` 的前提是 **f 在 t 的两侧都存在且同属一个光滑分支**。三种常见破坏方式：

| 破坏方式 | 表现 | 本次实例 |
|---|---|---|
| 参数被钳位 | 差分跨过钳位面，取到单边增量 | `target_pos` 的 `u` 钳位 → 76.9 g |
| 分段拼接 | 差分的左右两侧属于不同多项式段 | Waypoints 接缝 |
| 域边界 | t-h 落在定义域外，被静默钳位成 f(0) | 开放路径起点 |

第三种最隐蔽，因为**代码不报错**：`pos(-h)` 返回起点位置，差分于是把"静止"和"运动"平均了。

### 通用修法

1. **能解析就别差分。** 圆弧的导数 `v = omega x r`、`a = omega x (omega x r)` 是闭式的；用差分数值去验证解析几何是双误差叠加。本次 `Arc` 改为闭式后，`|a - dv/dt| = 2.1e-13`。
2. **必须差分时，按位置选格式：**
   - 内部：中心差分，O(h²)。
   - 边界：单侧二阶 `(-3f(0) + 4f(h) - f(2h)) / 2h`，同为 O(h²)，不需要域外样本。
   - 分段拼接点：**不要在那里比较导数**。那里加速度本来就是阶跃的，比的是两侧的平均值，测的是歧义不是缺陷。
3. **让差分步长服从被测对象。** 检查"速度是否是位置的导数"时用 h=1e-3 s；检查"这一帧承受了几个 g"时用帧间隔的分数。两者混用会让一个 1e-9 的真实误差被报告成 3e-3（见第 6 节）。

## 3. Waypoints 接缝的速度台阶（0.035 m/s）

### 现象

闭合巡逻航线的接缝处：位置连续、朝向连续（所以旧测试通过），但**速度有一个 0.035 m/s 的台阶**，相对 9 m/s 的 0.4%。每绕一圈抖一次。

### 根因（两层）

**第一层：端点切线按单元缩放。**
Hermite 的端点切线按"所在单元的弦长"缩放，于是共享同一个拐点的左右两段各自算出一套切线，`dp/dq` 相差两段弦长之比（实测 20%）。航线到达首个航点时比离开时快 20%。

修法：切线**按拐点**缩放，用相邻两段弦长的均值，两端共享同一个值。

**第二层（更本质）：弧长表的反查是分段线性的。**
`dq/darc` 取的是弧长表逐单元割线，即分段线性反函数的精确导数——它在**每个拐点上都是阶跃的**。所以速度在每个航点都跳一下，接缝只是最明显的那一处。

修法：把反查换成 **C1 三次 Hermite**，节点斜率用解析值 `dq/darc = 1/|dC/dq|`，并加 Fritsch–Carlson 限幅防止单元内回退。

### 修后

```
接缝速度台阶         6.6e-03 -> 4.97e-09 m/s
全程速度恒定性       8.956..9.045 -> 9.000000..9.000575 m/s
内部 |accel - dvel/dt|   中位数 1.2e-10，最大 1.9e-09
```

### 一个被撤销的"改进"，值得记下来

中途试过把弦长累加换成梯形积分（更准确的弧长）。**结果更差**：接缝台阶从 6.6e-3 涨到 2.9e-1 m/s。原因是 `_at()` 的 `dq/darc` 与被描述的那张表是一个**配套**，只改一边就破坏自洽。已回退并在代码里留下警告注释——不要在没有同步修改 `_at()` 的情况下"优化"这张表。

## 4. 包线适用矩阵：先问怎么动的，再问是什么

诊断脚本首次跑全库时报 4061 条违规（口径：脚本当时把所有非静止对象都按固定翼判）。真正需要改运动的只有十位数，其余全部是**对不适用的对象套了不合适的判据**。下面这张矩阵就是用来把两者分开的。

> 口径说明：文中的"修改前"数字（754.4 m/s²、4061 条、速度台阶 0.035 m/s）都是在**修复前的代码上实测**的，写这份报告时代码已改，因此无法用当前代码复现。修复后的数字与当前 `out/motion_report.json` 一致，可随时重跑核对。

### 4.1 四个包线类别

| 类别 | 判据 | 检查 | 不检查 |
|---|---|---|---|
| **airframe**（fighter / airliner / uav_fixed / uav_rotor） | 场景声明了航迹或驻留包线 | 速度上下限、加速度、过载、坡度、爬升率、航迹角、最低高度、转弯率、加加速度 | — |
| **camera**（挂载） | 任何相机 | 只查"不许瞬移"的速度上限 | 最低高度（1.7 m 眼高是对的）、转弯率（云台本来转得快）、导数（`rig.vibration` 让位置和速度按设计不同步） |
| **static / ground**（布景） | 无 `kinematics` 且非飞行 | 位置恒定 | 速度下限（停着的东西不是失速） |
| **explicit**（裸 vel） | 无航迹、无 path、无 seeker 反解 | 自洽性 + 极宽的合理上限 | 一切气动判据 |

### 4.2 同一字段在不同模式下语义不同

**这是包线误判的唯一来源。**

| 模式 | 判定依据 | 速度来源 | 检查什么 |
|---|---|---|---|
| trajectory | `clip.trajectory` / `objects[].trajectory` | 航迹解析 | 完整包线 |
| platform | `clip.seeker.mode == platform` | 裸 `vel`（此时它就是真速度） | 平台完整包线；目标按驻留处理 |
| linear seeker | `clip.seeker.profile == linear` | **seeker 反解值** | 自洽性 + 连续性 + 包线（用反解速度） |
| explicit | 无 clip 无 path | 裸 `vel` | 仅自洽性 |

关键结论：

> **裸 `objects[].vel` 在 linear seeker 模式下会被反解覆盖，因此不能作为包线判据；在 platform 和 explicit 模式下它就是真速度。同一字段在不同模式下语义不同。**

实测证据：`sk_air_uav` 的裸 `vel` 是 10.0 m/s，实际飞 **150.99 m/s**，差 15 倍。若拿 10 m/s 去判 `uav_fixed` 的 20 m/s 失速下限，会报一个完全健康的轨迹失速。

### 4.3 两个具体的分类缺陷（已修）

- **`flight_class` 写在 `clip.trajectory` 里而不是对象上。** `demo_air_uav` 的四旋翼在 trajectory 块里声明 `"flight_class": "uav_rotor"`。分类器只读对象，于是按模型名判成固定翼，再用 20 m/s 失速下限去判一个 25 m/s 的多旋翼。现在先读对象、缺则回落到 trajectory 块。
- **`yaw_rate_max` 原来是固定常数，与 `max_bank_deg` 自相矛盾。** 4 m/s 的飞机在 45° 坡度下本来就转 28 °/s，12 °/s 的上限把合法转弯判成非法，而 200 m/s 的飞机从不被检查。现在对气动类别按 `omega = g·tan(phi_max)/v` 逐帧推导，两条规则再也不可能打架。

### 关于那三个 8.485 m/s 的场景

`ds_air_uav` / `hero_air_uav` / `final_air_uav` 三个场景没有 `clip`、没有航迹、没有 `kinematics`，对象就是一条裸 `vel: [6, 6, 0]`。

**它们现在按 explicit 判，不报违规。** 理由是判据的前提不成立：包线检查的含义是"这个对象受气动约束在飞行"，而这三个场景从未声明这件事——没有航迹、没有包线、没有失速限制。拿固定翼的 20 m/s 失速下限去判它，判的是作者没写过的意图。

如果要让它们受气动约束，正确做法是**在场景里声明**（加 `kinematics` 或 `flight_class`），而不是让检查器猜。一架 900 m 高度以 8.5 m/s 平移的固定翼确实是失速状态；但那是场景数据的取舍，不是检查器该替作者做的决定。若将来要坐实为真实巡航，建议 `max_speed_mps` 取 160 左右（该机型的巡航量级）。

## 7. 已知局限

1. **包线是采样检查，不是连续证明。** 逐帧通过只在采样点上排除了越界；两帧之间可能存在更窄的尖峰。缓解手段是把 `dt` 调小重跑，而不是声称已证明连续。
2. **seeker 模式下 `objects[].pos` 会被反解覆盖。** `sk_air_uav` 写的是 `pos=[0, 0, 900]`，实际解出 `[27.8, 4866.3, 1280]`，偏移 4881 m。这不是 bug——距离/方位是反解的输入，位置是被求解的结果——但**写场景的人必须知道手填的 pos 在这个模式下不生效**。
3. **explicit 模式的 8.485 m/s 仍是物理上不可能的固定翼速度**（见 5 节）。本次只做了判据归位，没有改那三个场景的数据，因为那会改变已出图的数据集。
4. **`Arc` 不再提供转速渐变。** 早先的 `entry_ramp_s` 已删除：圆弧的速度就是 `r·omega`，把 omega 从 0 渐入等于让飞机在 t<0 时**原地不动**再从原点加速，那不是"进入转弯"而是"汽车起步"。真正的平滑进入是回旋线（曲率连续变化），不是一个能加在圆上的参数。需要平滑进入的场景应改用 `FlightManeuver`。
5. **航点航线在拐点处加速度是阶跃的。** 这是分段三次样条的固有性质（C1 但曲率只有 C0），不是缺陷；检查器在拐点报加加速度尖峰正是这个原因。
