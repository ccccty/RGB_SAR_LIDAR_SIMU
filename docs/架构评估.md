## 摘要

工程质量高于同规模的科研原型：错误路径普遍被显式拒绝（`scene.load_object_mesh` 拒绝
"写了 model 却不是 obj"、`materials.physical_face_materials` 拒绝从 MTL 颜色反推物理
属性、`ecm.load` 拒绝 bool 冒充数字），注释几乎都在解释"为什么"而不是"是什么"，关键
物理决策都留了实测数字。**12 个测试文件、113 个 `test_*` 方法，其中 110 个通过。**

但就在审查期间，新出现的 `tests/test_motion_realism.py` **15 个用例有 3 个未通过
（2 失败 + 1 错误）**。它揭出的两类问题性质不同：一类是 `motion.py` 的真实数值缺陷
（目标加速度读出 5.86 m/s²、演示场景的导数自洽误差 3.3e-3），另一类是**测试追不上库**的
API 漂移——`motion.Arc` 的构造签名里已经没有 `entry_ramp_s`，测试还在用它构造，
于是最强的那个不变量用例**直接崩在构造阶段、根本没跑到断言**。
后者尤其值得警惕：它让"导数自洽"这条检查静默失效，而 `selftest` 仍显示全绿。
这是本报告的第一优先级。

真正的问题分四类：

1. **一个上帝对象套着三个**——`dataset.run`（587 行）、`radar.simulate`（552 行）、
   `sar.simulate`（389 行）、`plan.ClipPlan`（681 行）、`studio.py`（1295 行）、
   `ecm.radar_apply`（141 行）；
2. **"输出目录布局"这一份知识被复制了 20+ 遍**，改命名不报错、只静默少数据；
3. **配置层有"写了没人读"的字段**（`randomize` 的 9 个子键、`_frame_index`），
   维护者会以为它们在起作用；
4. **一个显示设置会改变一个物理量**——`ir.render` 的 `apparent_temp_k` 随
   `preview_mode` 变化，实测差 **58.9 K**（死像素），而它是 `selftest` 的判据。

按严重程度：

| 级别 | 数量 | 代表问题 |
| --- | --- | --- |
| **A. 会导致错误结果** | 5 | 运动导数一致性未验证（最强的用例崩在构造阶段）+ 加速度越界、`apparent_temp_k` 随显示模式变化、三套波段表 + L/S/C 全落到 X 的衰减、`fr_cfg` 被跨模态就地改写、`randomize` 是"改了不生效"的陷阱 |
| **B. 会让维护困难** | 13 | 六个上帝对象；目录布局散落；`_compose` 用控件默认值推断意图；模态列表硬编码 9 处；场景 82% 重复；`meta.json` 无 `ecm` 段 |
| **C. 风格与一致性** | 10 | `_face_normals` 三份逐字节相同；`_profile` 同文件重复定义；同名不同义的三个 `_number`；`path` 三重含义 |

**最该先做的四件事**：
1. 先把 `test_motion_realism.py` 的 `Arc` 旧签名改对，让导数契约用例重新跑起来，
   再修目标加速度 5.86 m/s² 与演示场景的 3.3e-3 自洽误差（9.1）；
2. 把 `apparent_temp_k` 从 `preview_mode` 里解耦（一个显示开关不该决定返回的物理量）；
3. 给 `scene.prepare_mesh` 加进程内缓存（约 20 行），340 帧数据集从"多花 32 分钟"降到秒级；
4. 波段表收敛为一份，且拒绝叫不出名字的 `fc_ghz`（现在 L/S/C 静默套用 X 的雨衰）。

### 1.1【B】`dataset.run` 是一个 587 行的"五传感器 + 六套标注 + 统计 + 元数据"函数

- **位置**：`simkit/dataset.py` 的 `run()`（253-839）；`merge_parts`（860-1063）把统计逻辑又写了一遍。
- **问题**：`run` 内部串了 8 类彼此无关的事：

  | # | 职责 | 位置 |
  | --- | --- | --- |
  | 1 | 配置解析与归一化 | 253-280 |
  | 2 | 目录规划（**手写 `dirs` 字典**） | 285-310 |
  | 3 | COCO 骨架构造（4 个 dict × N 视场 × M 波段） | 312-330 |
  | 4 | Blender 外渲染整段调度 | 333-352 |
  | 5 | 五个模态的渲染 + 写图 + 写标注 + 累加 COCO | 354-660 |
  | 6 | 分块文件名规则 | 668 与 `anno_name` |
  | 7 | **从磁盘反读全部 COCO 重建统计** | 700 附近起 |
  | 8 | `meta.json` 与干扰导出 | `run` 尾部 |

- **影响**：
  - 新增一个模态或一个视场 tag，要同时改 6 处（`dirs`、`coco_*`、渲染分支、标签写出、`stats`、`meta`）；
  - `run` 的统计（`stats["frames"]` 起，在 `run` 尾部）与 `merge_parts` 的统计（在该函数内）是
    **两份独立实现**。任何一侧加了统计字段，另一侧就静默缺失——**分块跑和不分块跑会得到
    不同的 `stats.json`**，而 `cli.cmd_gen --part`（`cli.py:30-46`）正是常规用法。
  - 已经留下痕迹：`meta["interference"]` 在三处被赋值（`run` 内两处、`merge_parts` 内一处），
    三处的键集合靠人工保持一致。
- **建议**：按模态切 `simkit/writers/{optical,ir,radar,lidar,sar}.py`，每个暴露
  `write(ctx) -> None`，`run` 只保留"遍历帧 → 分发 → 汇总"。统计构造抽成
  `stats.build(...)` 由 `run` 与 `merge_parts` 共用。

### 2.3【A】波段配置存在三套互不相同的表，且 L/S/C 静默套用 X 的雨衰

| 表 | 位置 | X | Ku | 其余 |
| --- | --- | --- | --- | --- |
| `weather.RADAR_BANDS` | `weather.py:31-38` | **9.5** | **15.0** | K/Ka/W/W94，带 beamwidth、gas_db_km、rain_k/rain_a |
| `sar.BAND_FC` | `sar.py:42` | **9.6** | 15.0 | **C 5.4 / L 1.3 / S 3.0**（weather 表没有这三个） |

- **实测一（波段名就近匹配会把 L/S/C 全认成 X）**：

  ```

  radar_band_of(3.0 GHz) = 'X'     ← S 波段
  radar_band_of(5.4 GHz) = 'X'     ← C 波段
  radar_band_of(9.6 GHz) = 'X'
  radar_band_of(15.0/15.5) = 'Ku'
  ```

  因为 `radar_band_of`（`weather.py:265`）是"取最近的中心频率"，而
  `RADAR_BANDS` 的表头是 `X(9.5) Ku(15.0) K(24) Ka(35) W(77) W94(94)`——**全部 ≥ 9.5**。

  一次 4 km 双程、L 波段 SAR 实际应几乎不衰减，但代码取 `att["X"]=0.470` 得
  `2×0.470×4 = 3.8 dB` 的假衰减（真实 L 波段约 0.02 dB）。

- **影响**：这是**会算错结果的 A 级问题**，而且只在"用 L/S/C 波段 + 有降水"时出现，
  测试覆盖不到（`test_radar_realism` 全部用 X/Ku）。
- **建议**：
  1. 以 `weather.RADAR_BANDS` 为唯一真源；`sar.BAND_FC` 改为
     `{k: v["fc_ghz"] for k, v in RADAR_BANDS.items()}` 再补 C/L/S 三项（附注释说明
     "weather 表不含这些波段，其雨衰按 ITU-R P.838 外推"）；
  2. studio 的 `fc_ghz` 引用同一张表，中文备注留在注释里；
  3. **`radar_band_of` 改成"找不到就返回 None"**，让调用方显式拒绝，而不是就近匹配到 X。
     `radar.py:393`/`sar.py:450` 的 `.get(...)` 已经是"取不到就 0 dB"的静默路径，
     两者叠加就是"波段写错 → 不下雨 → 结果看起来正常"。

## 3. 耦合：改一个模态会不会影响另一个

### 3.1【A】五模态共享同一个 `world`，且 `fr_cfg` 被就地改写

- **位置**：
  - `dataset.py:369`（`fr_cfg["_ecm_t"] = float(t)`，在 `build_world` **之前**，正确）；
  - `dataset.py:371-373`（`world` 建好后立刻 `o["cls_id"] = ...` 就地写 `world.objs`）；
  - `dataset.py:381-390`（把 `radar/lidar` 的 `pos/look_at/vel` 写回 `fr_cfg`）；
  - `dataset.py:449-451`（再写回 `fr_cfg["_ecm_t"]`、`_frame_t`、`_frame_index`）；
  - `dataset.py:583`（SAR 分支写回 `fr_cfg["_frame_t"] = 0.0`）。
- **问题**：`fr_cfg` 就是 `plan.state()` 产出的那份配置 `s["cfg"]`。**分支执行顺序是
  ir → radar → lidar → SAR → optical**（实测：396 / 444 / 537 / 568 / 624）。
  SAR 在**帧循环中间**把 `_frame_t` 改成 `0.0`，之后 optical 分支读到的是被 SAR 改过的字典。
  当前 optical 不读这些键，所以没有可见 bug——但这正是"改一个模态影响另一个"的结构性入口，
  而且这个入口现在有**四处写入**。
- **影响**：未来任何模态只要读 `_frame_t`，就会拿到 SAR 写的 `0.0`；
  模态执行顺序一变，污染方向也变。`_frame_t` 在 `sar.py:263` 已经被读取
  （`t = float(cfg.get("_frame_t", ...))`），所以这个耦合**已经实际生效**。
- **建议**：把"这一帧的时间 / 序号"从 `fr_cfg` 里拿出来，作为**显式参数**传给需要它的模态：
  `sar.simulate(world, cfg, t=...)`、`radar.simulate(world, cfg, t=..., frame_index=...)`。
  `fr_cfg` 只读，不再承担"帧级上下文"的职责。

### 3.2【B】SAR 的主目标与 `plan` 的主目标来自两套独立规则

- **位置**：`dataset.py:578` 的
  `tgt = next((o for o in cfg["objects"] if o.get("label", True)), None)`
  vs `plan.py` 的 `self.targets = [...]; self.target = self.targets[0]`。
- **问题**：两者目前结果相同（都取第一个带 `label` 的对象），但 `plan` 在 `ClipPlan.__init__`
  里会对重名对象抛错，而 `dataset` 这行是**在 `plan` 之外重新扫一遍 `cfg["objects"]`**，
  完全绕过了那道校验。将来 `plan` 换了选主目标的规则（例如按 `cls` 挑），
  SAR 会锚到一个和轨迹目标不同的对象上，且不会报错。
- **建议**：`plan.state()` 多带一个 `primary_object` 字段（名字或 id），`dataset` 读它，不再自己扫。

### 3.3【B】`sensors` 与 `clip.views` 是两个并行的"相机真源"

- **位置**：`plan.state()` 把**所有** `sensors.*` 的 `look_at` 统一成主视场瞄准；
  `dataset.py:381-390` 又对 `radar/lidar` **再覆盖一次**（用 `_view_pose(s, views[0], cfg)`）。
- **影响**：后写的覆盖先写的，所以当前行为是"radar/lidar 跟随 view[0]"。这个物理约定
  （雷达/激光与主相机共孔径）同时写在两个模块里，删掉任意一处都会悄悄改变几何，
  且没有测试能发现（`test_aviation` 的 `singleton_chunks_and_clip_boundaries` 只断言了
  `sensors.radar.vel`）。
- **建议**：约定收进 `plan`：`state()` 直接给出 `sensors.radar/lidar` 的最终位姿并注明原因，
  `dataset` 只读不写。

### 3.5 结论：改一个模态的实际影响面

| 改什么 | 会影响别的模态吗 | 原因 |
| --- | --- | --- |
| `ir.render` 的灰度窗口 | 不会 | 只读 `cfg["ir"]` |
| `radar.simulate` 的波束/检测 | **间接会** | 它写 `fr_cfg["_ecm_t"]`/`_frame_t`/`_frame_index`（449-451） |
| `sar.simulate` 的 anchor | **会** | 写回 `fr_cfg["_frame_t"]=0.0`（583），而 optical 在其后执行 |
| `ecm.attach` 的实体几何 | **会（全模态）** | 它进的是共享 `World`，光学的遮挡、激光的回波、雷达的射线全部受影响 |
| 任何模态的 box 约定 | **会（全模态，有意为之）** | 统一走 `_boxes_for`（138-174），注释写明了原因。这是**好的耦合**，应保留 |
| 目录命名 | **会（全导出链）** | 见 1.4 |

## 5. 命名一致性

### 5.1【B】`path` / `trajectory` / `motion` 三个词描述同一件事，且 `self.path` 有三重含义

| 位置 | 用的词 | 实际含义 |
| --- | --- | --- |
| `plan.py:136` | `clip.observer_trajectory` | 相机轨迹 spec |
| `plan.py:148` | `clip.trajectory` | 目标轨迹 spec（`world` 模式） |
| `plan.py:137` | `self.path`（`independent_flight`） | **相机**路径 |
| `plan.py:144` | `self.path`（`platform`） | **载机**路径 |
| `plan.py:148` | `self.path`（`world`） | **目标**路径 |
| 每个 object 的 `trajectory` | `trajectory` | 非主目标轨迹 |
| `obj["motion_type"]` | `motion_type` | 只有 "ground" 一个值，作用是贴地约束 |

- **影响**：`self.path` 同一属性三种含义，是 `plan.py` 最容易读错的地方。
  `motion_type` 这个名字会被误读为"运动类型枚举"（实际只有一个取值、只做一件事）。
- **建议**：`self.path` 拆成 `target_path` / `observer_path` / `platform_path`
  （`observer_path` 已存在，见 137 行）；`motion_type` 改名 `ground_constraint`。

### 5.2【B】"视场"有三个键名：`name` / `tag` / `sensor`

- **位置**：`plan._build_views`（279-307）产出的 view dict 同时含 `name`、`tag`、`sensor`；
  `plan.state` 再补 `pos/look_at/fov_deg/width/height/roll_deg`；
  `dataset._views_of`（70-93）只用 `name` 与 `tag`。
- **问题**：`tag` 是**目录后缀**（`""` 或 `"_wide"`），`name` 是**视图名**（`"seeker"`/`"wide"`），
  `sensor` 是**用哪个 capture 配置**。三者语义不同却经常被混用：`dataset` 用 `tag` 拼目录、
  又用 `name` 查 `view_px`、`studio` 又用 `name` 做显示。
- **建议**：改名 `dir_suffix` / `view_name` / `capture_key`，至少加一条注释说明三者分工。

### 5.3【C】同一概念在 dataset 与 studio 里叫法不同

| dataset.py 的目录名 | studio.py 的键 | 备注 |
| --- | --- | --- |
| `images/radar` | `radar` **和** `radar_rd` | 两个键指向同一个目录 |
| `images/radar_ra` | `radar_ra` | 一致 |
| `images/ir_lwir` | `lwir`（去掉 `ir_` 前缀） | `MOD_PREF` 里是裸波段名 |
| `labels/lidar` | `lidar` / `lidar_range` / `lidar_intensity` | 三个键指向同一目录 |

- **影响**：`studio._label_dir_name`（875-892）必须维护一张桥接映射表；
  注释记录过一次事故（模糊匹配让雷达卡片显示了红外框）。
- **建议**：与 1.4 的 `layout.py` 合并解决；studio 的 `MOD_CN` 只负责"结构化元组 → 中文标签"。

### 5.4【C】`labels` 与 `observations` 的字段命名风格不同

- `observations.py:47-56` 用 `center_world_m` / `origin_world_m` / `velocity_mps`（**带单位后缀**）；
  `labels.radar_labels`（99-125）用 `center` / `size` / `yaw`（**不带单位**）。
- **影响**：消费方（`check_aviation.py`、`export_web.py`）必须分别处理两套命名。
- **建议**：统一到 `observations` 的风格（`_m` / `_mps` / `_deg`），`labels.radar_labels` 跟上。

### 5.5【C】`ecm` 的实体 id 与 `world.objs` 的 id 是两个命名空间

- **位置**：`ecm.attach`（938-1009）；实体用字符串 `id`（`"escort_jammer"`），
  `world.objs` 用整数 `id`。代码靠 `ent["id"]` / `o["id"]` 区分，但两者都在同一个
  `attach` 里流转，且 `ecm` 实体**故意不进标签**
  （`test_the_cloud_is_geometry_in_the_world_and_label_free`）。
- **建议**：这不是错误，但要在 `ecm.attach` 的 docstring 里明确
  "字符串 id 是配置命名空间，整数 id 是渲染命名空间"，避免后续有人把两者混用。

## 8. 性能瓶颈

> 全部实测（`cProfile` + `perf_counter`，Python 3.13，纯 numpy，Windows）。

### 8.1【A】每帧重新解析并抽稀全部 OBJ（最大瓶颈）

- **位置**：`scene.build_world`（`scene.py:91-188`）→ `scene.prepare_mesh`（`scene.py:67-88`）
  → `mesh.load_obj`（`mesh.py:309`）+ `mesh.decimate`（`mesh.py:185`）+ `mesh.clean_faces`。
- **实测**（同一进程内连续调用两次）：

  ```
  场景                            目标数  面数     第 1 次     第 2 次
  sk3_high_air2air                  1     9,735     284 ms     278 ms
  ds_ground_vehicle                 6    12,474    5,621 ms   5,607 ms
  sk3_low_air2ground_clutter       12    28,635    9,293 ms   9,452 ms
  ```

  **第二次不比第一次快**：`prepare_mesh`（`scene.py:67-88`，共 22 行，**无任何缓存**）
  每次调用都重新 `load_obj` + `decimate` + `clean_faces`。
- **影响**：
  - `ds_ground_vehicle`（**340 帧**）= 340 × ~5.6 s ≈ **32 分钟纯网格准备**；
  - `sk3_low_air2ground_clutter`（240 帧）≈ **37 分钟**；
  - 这部分计算**与帧号完全无关**，是纯浪费。
- **建议**（按收益排序）：
  1. **给 `prepare_mesh` 加进程内缓存**（≈20 行）。键用
     `(abspath(model), st_mtime_ns, st_size, decimate, scale, height)`，值缓存
     `(mesh, lo, hi)`。安全性：`Mesh.with_geometry`（`mesh.py:48`）返回新对象，
     `build_world` 之后只做 `m.transformed(...)`，不会就地改写缓存值。
  2. **`decimate` 的二分可以省**：`scene.py` 传的是 `target_tris`，于是每次都跑满多轮二分、
     每轮一个完整 `np.unique(axis=0)`。可按 `target/len(faces)` 直接估一个起始 `grid`，
     再补 1–2 次修正。
  3. **`np.unique(axis=0)` 换线性化键**：`np.unique(k0*A + k1*B + k2)` 比 `axis=0`
     的 lexsort 快 3–5 倍。

### 8.2【B】`plan_frames` 每个 clip 都完整走一遍 `prepare_mesh`

- **位置**：`plan.py:109` `object_size_m(self.target, ...)` → `plan.py:67-74` → `scene.prepare_mesh`。
- **实测**：`ds_ground_vehicle` 的 `plan_frames(3)` 共 1.66 s，其中 `ClipPlan.__init__` 内的
  `object_size_m` 单独占约 90%。
- **影响**：studio 的预览按钮、`validation.inspect`、`plan.summary`（811-867，
  对每个 clip 都构造一次 `ClipPlan`）都会触发。
- **建议**：与 8.1 共用缓存；更彻底的做法是让 `asset.expand`（`asset.py:157-208`）把
  `scaled_bbox_m` 直接写进 spec，`plan` 直接读，根本不必碰网格。

### 8.3【B】`radar.simulate` 是单帧最贵的一步，且每帧重建材质表与面几何

- **位置**：`radar.py:163-714`（**552 行**）；`radar.py:199-200`；`radar.py:203`。
- **实测**：`sk3_high_air2air`（40×28 波束 × 1024 距离门 × 256 chirps）约 **18.8 s/帧**；
  `sk3_low_air2ground_clutter` 约 **20.5 s/帧**；该场景只有 9,735 面，
  说明成本主要不在面数而在 **多普勒/距离处理链**。
- **可优化项**（按确定性排序）：

## 10. 特别关注项

### 10.1 `dataset.py`（1063 行）与 `studio.py`（1295 行）是不是承担了太多职责？

### 10.2 `interference.py` 的图像层方案与场景级 `ecm.py` 如何共存

> 场景级方案已经以 `simkit/ecm.py`（1009 行）的形式落地，有 20 个测试和一个演示场景。

#### 两套方案的实际边界（读代码得出，非推测）

| | `interference.py`（图像层） | `ecm.py`（场景级） |
| --- | --- | --- |
| 配置键 | `cfg["interference"]` | `cfg["ecm"]` |
| 作用时机 | 全部渲染**完成后**，对 `images/**/*.png` 做像素扰动 | 渲染**过程中**，进 `World` 与 `radar.simulate` |

| 默认 | 关闭 | 关闭（未配置时旧数据集逐字节不变） |

**它们不冲突的原因**：层次不同。图像层是**增广**（生成后可丢弃、可重建、源数据不动）；

**唯一的重叠点**：`scenes/validation_fighter` 与 `validation_fighter_interference`

字段的差别。

#### 必须立刻对齐的两处接口

1. **`meta.json` 缺 `ecm` 段（追溯缺口，见 9.3）**。4 行代码，但决定了数据集能不能被复现。
2. **`validation.inspect` 不认识 `ecm`（预检缺口，见 9.4）**。1 行代码，让非法块在毫秒级失败。

#### 一句话

图像层（`interference.py`）是**增广**，场景级（`ecm.py`）是**建模**；两者应当长期共存，
